Design / platform boundary

macOS backend

The architecture is in development. macOS execution is not available in a Heimdall release yet.

One CLI, no always-on service

The heimdall CLI remains the only command users invoke. Transparent operation will require an optional signed companion and system extension, but it will not install a persistent user-managed Heimdall daemon. The provider is enabled only while at least one transparent run is active.

No implicit fallback. A failed transparent run never switches to an explicit proxy or the normal network path. The command starts only after registration succeeds.

Two backends with different claims

BackendPurposeBoundary
macos-explicitCLI-only compatibility for cooperative proxy clients.Client-dependent TCP; no transparent UDP, fake DNS, QUIC, runtime TLS, strict scope, or fail-closed claim.
macos-transparentOptional signed transparent TCP/UDP path.Process attribution must pass native tests before it can approach the Linux cgroup claim.

The explicit backend never edits system-wide proxy settings. NEAppProxyProvider remains a possible managed per-app option, not the default backend for arbitrary terminal commands.

Signed transparent path

  1. The CLI validates policy, opens the per-run relay and JSONL store, and starts the command in an initially stopped process group.
  2. A signed companion registers the run with an NETransparentProxyProvider system extension.
  3. The provider uses the flow audit token to classify the source process against the registered process group and parent chain.
  4. Unrelated flows return to their normal route. Attributed flows use an authenticated loopback channel to the CLI-owned relay.
  5. The CLI relay owns policy, proxy/direct/reject routing, capture, relay TLS, and evidence.

This starts as a process-group best-effort boundary. Process-group escape, PID reuse, races, and ambiguous concurrent attribution must be measured; they are not hidden behind a Linux-equivalent claim.

Foreground-owned lifecycle

  • A session helper exists only for its run and unregisters on completion or owner death.
  • Matched flows fail closed if the provider or relay disappears.
  • Loopback, helper, provider, and CLI-owned upstream traffic are excluded to prevent recursion.
  • Concurrent runs use separate identities, secrets, relays, and logs. Ambiguous overlap is rejected.
  • The final run disables the transparent configuration; stale recovery rejects PID reuse and writes evidence.

Capabilities arrive separately

CapabilityInitial status
TCPFirst transparent milestone after IPv4/IPv6, relay-loss, backpressure, and long-lived flow tests.
UDPSeparate milestone preserving datagram and destination boundaries.
DNS and fake DNSObserved hostname metadata is not universal DNS coverage; fake DNS is unavailable initially.
QUICUnavailable until UDP migration, rebinding, and policy correlation pass.
Runtime TLSUnavailable on macOS.
Relay TLSLater milestone after transparent TCP and explicit trust acceptance.

Native release gate

A compile is not acceptance. A signed, entitled Apple-silicon installation must prove TCP/UDP, process descendants and escapes, two concurrent runs, unrelated-process isolation, owner/provider/relay failures, DNS boundaries, recursion protection, JSONL integrity, cleanup, approval, upgrade, rollback, and uninstall.

Until that matrix passes, package pages, heimdall agent, the website, and release notes must continue to say macOS is not available.

Design / platform boundary

macOS backend

Apple silicon can run the reduced macos-explicit backend from source. Official macOS packages and transparent support are not available yet.

One CLI, no always-on service

The heimdall CLI is the only process a user starts. The explicit backend owns one kernel-assigned loopback listener and one private JSONL run store, then closes both with the foreground command. It starts no daemon, helper, Web UI, app, or system extension and never changes system proxy settings. No persistent user-managed Heimdall daemon is installed or required.

Native explicit acceptance passed. On Apple silicon, just test-macos-native routes curl through the loopback SOCKS5 CONNECT frontend, the shared relay_transport, and a fixture upstream; it verifies hostname preservation, policy and flow evidence, listener cleanup, exit propagation, and pre-exec refusal. This is source-backend evidence, not official package or transparent acceptance.

No implicit fallback. A failed transparent run never switches to an explicit proxy or the normal network path. The command starts only after registration succeeds.

Explicit quick start

heimdall agent --policy default

# Use actions.execute_prefix from that JSON. Its shape is:
heimdall --config /path/to/config.toml run \
  --backend macos-explicit --policy default -- \
  curl https://example.com

Readiness requires Apple silicon, system DNS, rejected UDP, capture off, decrypt off, and readable outbound credentials. The child receives only ALL_PROXY and all_proxy with a socks5h://127.0.0.1:<port> URL. A client can ignore those variables, so this mode is cooperative rather than transparent or fail closed.

Two backends with different claims

BackendStatusBoundary
macos-explicitAvailable from source on Apple silicon; package pending.Cooperative TCP route/direct/reject and metadata only; no strict scope, UDP, fake DNS, capture, TLS inspection, QUIC, or fail-closed claim.
macos-transparentIn development.Optional signed companion; process attribution and transport require separate native acceptance.

Explicit policy and flow records use source={backend:"macos-explicit", scope:"cooperative_environment"}. That proves the client reached the listener, not operating-system process attribution. A normal run intentionally records incomplete descendant cleanup because the environment cannot prove the entire process tree used it. NEAppProxyProvider remains a possible managed per-app option, not the default backend for arbitrary terminal commands.

Signed transparent path

  1. The CLI validates policy, opens the per-run relay and JSONL store, and starts the command in an initially stopped process group.
  2. A signed companion registers the run with an NETransparentProxyProvider system extension.
  3. The provider uses the flow audit token to classify the source process against the registered process group and parent chain.
  4. Unrelated flows return to their normal route. Attributed flows use an authenticated loopback channel to the CLI-owned relay.
  5. The CLI relay owns policy, proxy/direct/reject routing, capture, relay TLS, and evidence.

This starts as a process-group best-effort boundary. Process-group escape, PID reuse, races, and ambiguous concurrent attribution must be measured; they are not hidden behind a Linux-equivalent claim.

Native release gate

The explicit source gate is complete, but official artifacts still need checksum, clean-machine install, upgrade, rollback, uninstall, and fresh-run acceptance. Until then, npm, PyPI, Cargo, and GitHub release pages remain Linux-only.

The transparent backend still needs a signed, entitled installation proving TCP/UDP, process descendants and escapes, concurrent and unrelated-process isolation, provider/relay failures, DNS boundaries, recursion protection, JSONL integrity, cleanup, approval, upgrade, rollback, and uninstall. None of those claims come from explicit mode.
